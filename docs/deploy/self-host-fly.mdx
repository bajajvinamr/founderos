---
title: Self-host on Fly.io
summary: Deploy a single-tenant FounderOS instance to Fly.io in minutes
---

FounderOS uses a **one Fly app per customer** model. Each instance gets its own Fly app, persistent volume, and isolated secrets. This guide walks you through a complete provision and first deploy.

## Prerequisites

- **flyctl CLI** — [Install](https://fly.io/docs/flyctl/install/) via `brew install flyctl` (macOS) or download
- **Fly.io account** — Sign up at [fly.io](https://fly.io), then log in locally
- **Postgres database** — Use Fly Managed Postgres, [Supabase](https://supabase.com), [Neon](https://neon.tech), or any Postgres host
- **This repo** — Clone and cd to the repo root

## Step 1: Set up Fly CLI

```bash
# Install flyctl (if not already installed)
brew install flyctl   # macOS
# or visit fly.io/docs/flyctl/install for other OSes

# Log in to your Fly.io account
fly auth login

# Verify login
fly auth whoami
```

## Step 2: Prepare your database

You need a Postgres database connection string in the format:
```
postgres://username:password@hostname:5432/database
```

**Option A: Fly Managed Postgres (recommended for simplicity)**

Create a managed database in the same region as your app (e.g., Mumbai `bom`):

```bash
fly postgres create --name founderos-db --region bom --initial-cluster-machine-count 1
```

This outputs a connection string. Save it for the next step.

**Option B: Supabase (if you already have a Supabase project)**

Copy your connection string from Supabase dashboard: Project Settings → Database → Connection string → URI.

**Option C: Self-hosted or other Postgres host**

Have your connection string ready.

## Step 3: Run the provisioning script

From the repo root, run:

```bash
export DATABASE_URL="postgres://user:password@hostname:5432/database"
./scripts/fly-provision.sh my-company
```

Replace `my-company` with your customer slug (kebab-case, will become `founderos-my-company`).

**What the script does:**
1. Creates a Fly app named `founderos-my-company`
2. Attaches a 3 GB persistent volume at `/founderos`
3. Sets the `DATABASE_URL` secret (auto-migrates DB on startup)
4. Generates and sets `FOUNDEROS_SECRETS_MASTER_KEY` (encryption key)
5. Deploys the app
6. Prints the live URL

**Example with Claude API enabled:**

```bash
export DATABASE_URL="postgres://user:pass@db.example.com/founderos"
export ANTHROPIC_API_KEY="sk-ant-..."
./scripts/fly-provision.sh acme-corp
```

The script will automatically pass `ANTHROPIC_API_KEY` to the deployed app.

**Options:**

| Flag | Default | Example |
|------|---------|---------|
| `--region` | `bom` (Mumbai) | `--region sin` (Singapore) — pick close to your DB |
| `--memory` | `1gb` | `--memory 2gb` — increase if needed |
| `--volume` | `3` (GB) | `--volume 5` — adjust persistent volume size |
| `--no-deploy` | Deploy immediately | `--no-deploy` — stage only, deploy later with `fly deploy` |

**Example with custom options:**

```bash
./scripts/fly-provision.sh acme-corp \
  --region sin \
  --memory 2gb \
  --volume 5 \
  --no-deploy
```

Then deploy when ready:
```bash
fly deploy --app founderos-acme-corp
```

## Step 4: Wait for the app to start

Fly.io starts a machine automatically. This takes 30–60 seconds. Monitor:

```bash
fly status --app founderos-my-company
fly logs --app founderos-my-company --follow
```

Once you see "Server running on..." in the logs, the app is ready.

## Step 5: Verify the deployment

Check the three health endpoints:

```bash
# Liveness (should return 200)
curl https://founderos-my-company.fly.dev/api/healthz

# Readiness (confirms DB connection + auth is ready)
curl https://founderos-my-company.fly.dev/api/readyz

# Full status (JSON with provider info, versions, etc.)
curl https://founderos-my-company.fly.dev/api/health | jq .
```

If all three return 200, your deployment is live.

## Step 6: Access the app

Open in your browser:
```
https://founderos-my-company.fly.dev
```

You'll see a login page (Better Auth is the default auth provider). Sign up to create the first account.

## Adding more secrets and features

### Enable Claude

If you didn't set `ANTHROPIC_API_KEY` during provisioning, add it now:

```bash
fly secrets set ANTHROPIC_API_KEY="sk-ant-..." --app founderos-my-company
```

Restart the app to pick up the secret:
```bash
fly deploy --app founderos-my-company
```

### Enable email (Resend)

```bash
fly secrets set RESEND_API_KEY="re_..." --app founderos-my-company
```

Then set the sender email in `fly.toml` and redeploy, or use:
```bash
fly config set EMAIL_FROM="noreply@mycompany.com" --app founderos-my-company
```

### Enable OpenAI

```bash
fly secrets set OPENAI_API_KEY="sk-..." --app founderos-my-company
```

### Check what secrets are set

```bash
fly secrets list --app founderos-my-company
```

Shows secret names only (not values, for security).

## Making the app public (internet-facing)

By default, the app is `private` — accessible only via the Fly URL with login required.

To enable public access (no login, anyone can use it):

Edit `fly.toml`:
```toml
[env]
  FOUNDEROS_DEPLOYMENT_MODE = "authenticated"
  FOUNDEROS_DEPLOYMENT_EXPOSURE = "public"
  FOUNDEROS_PUBLIC_URL = "https://founderos-my-company.fly.dev"
```

Then redeploy:
```bash
fly deploy --app founderos-my-company
```

For more details, see [fly-envs.md](./fly-envs.md) — exhaustive reference of all environment variables.

## Deploying updates

Whenever you push new code, redeploy with:

```bash
fly deploy --app founderos-my-company
```

The deployment is rolling — old machines shut down gracefully after new ones start. Database migrations run automatically on boot.

## Persistent volume

The 3 GB volume at `/founderos` survives deploys and machine restarts. It contains:
- Instance config and settings
- Encrypted secrets (including the master encryption key)
- Agent workspace and session state
- Database backups (if enabled)

It's automatically backed up by Fly's Postgres backup system if you're using Fly Managed Postgres.

## Single-tenant model: benefits & scaling

**Benefits of one app per customer:**
- Complete data isolation (separate DB, separate volume, separate secrets)
- Independent deploys — upgrade one customer without affecting others
- Transparent pricing — each app maps to one Fly billing entity
- Simple teardown — `fly apps destroy founderos-my-company` removes everything

**When to move to multi-tenant:**
Once you have 5+ customers, running N Fly apps becomes operationally heavy. At that point, consider:
- One Fly app with multi-tenant database schema (row-level isolation)
- Shared persistent volume
- Better per-customer resource allocation

For now, single-tenant is the recommended pattern.

## Health checks & monitoring

Fly automatically monitors two health check endpoints (configured in `fly.toml`):

| Endpoint | Check Type | Interval |
|----------|-----------|----------|
| `/api/healthz` | Liveness — is the process alive? | Every 5s |
| `/api/readyz` | Readiness — is the DB accessible + auth ready? | Every 30s |

If readiness fails, Fly temporarily stops routing traffic until it recovers.

You can manually check the rich status JSON anytime:
```bash
curl https://founderos-my-company.fly.dev/api/health | jq .
```

## Troubleshooting

**App won't start / readiness check fails:**
```bash
fly logs --app founderos-my-company --follow
curl https://founderos-my-company.fly.dev/api/readyz -v
```
Check for `DATABASE_URL` or encryption key issues in the logs.

**"DATABASE_URL not set" error:**
```bash
fly secrets list --app founderos-my-company
fly secrets set DATABASE_URL="postgres://..." --app founderos-my-company
fly deploy --app founderos-my-company
```

**Provider not available (Claude, OpenAI, etc.):**
```bash
fly secrets list --app founderos-my-company | grep ANTHROPIC_API_KEY
curl https://founderos-my-company.fly.dev/api/health | jq '.providers'
```

**Need to view a secret value (e.g., to verify it was set correctly):**
```bash
fly secrets show DATABASE_URL --app founderos-my-company
```

For more help, see [fly-envs.md](./fly-envs.md) for complete environment variable reference.
